# Mediqzy AI Customer-Care: Final Implementation Plan

Date: 2026-11-07

## V1 implementation update

Implemented as a headless, customer-safe API on 2026-11-07. This first release is deliberately deterministic: it does not call an LLM and therefore cannot turn a user prompt into a clinical answer or an unbounded tool call.

| Capability | Delivered surface | Safety boundary |
|---|---|---|
| Approved FAQs and policy answers | `POST /api/customer-care/conversations/:id/messages` | PostgreSQL full-text retrieval uses only published, non-expired tenant/global documents. The returned excerpt, document ID and document version are generated by the retrieval query as citations. Missing evidence creates a handoff rather than an answer. |
| Self-service status | `GET /api/customer-care/status/{appointments,lab-orders,pharmacy-orders,membership}` | Every request is authenticated; records are queried only for `req.user.id`. No clinical result content, payment decision or third-party data is returned. |
| Verified appointment discovery | `GET /api/customer-care/availability?doctorId=&date=` | Returns only explicit provider availability minus authoritative booked slots. It intentionally does not use legacy fallback/default schedule generation. |
| Appointment changes | `POST /api/customer-care/appointment-actions/proposals` and `/confirm` | Adapts the existing one-time token, ownership, current-state re-read, availability revalidation and idempotent appointment transaction. It supports only cancellation and rescheduling. |
| Durable human handoff | Customer conversation state plus `/api/crm/customer-care/handoffs` | One active handoff per conversation, queue, assignee, SLA, safe non-PHI summary and resolution status. CRM actions require the existing communication capabilities. |

The accompanying migration is `server/migrations/20261107000100-customer-care-v1.migration.js` and is included in `server/scripts/migrate-all.mjs`. Populate approved customer-support documents through `PUT /api/crm/customer-care/knowledge` before enabling a customer channel. Set `CUSTOMER_CARE_DEFAULT_TENANT_ID` for authenticated individual users that do not carry an organisation tenant, so their handoffs route to a server-configured support tenant.

Not implemented in V1: clinical advice, clinical-document interpretation, claims/refunds/payments/benefit decisions, employer/family access, voice, free-form autonomous actions, or direct model/database access. Such messages produce a durable human handoff.

## Status and decision

**Approved direction:** build a Mediqzy-native, headless customer-care capability embedded in the existing CRM and channel surfaces.

**Deferred:** Chatwoot. Do not configure, deploy, extend, or make new product dependencies on Chatwoot in this programme. Existing Chatwoot bridge code remains untouched and optional for a future workspace decision.

**Not in scope for the first release:** clinical diagnosis, prescription advice, autonomous clinical triage, automatic payment/claim decisions, direct database access by an LLM, voice bot calling, social/community features, and a replacement CRM.

## Executive architecture

```text
Patient web/mobile · CRM operator · WhatsApp/SMS/email
                         │
                         ▼
            Customer-care API (Mediqzy Node service)
  ┌────────────────────────────────────────────────────────────┐
  │ authenticated actor / tenant / purpose / consent resolution │
  │ input safety + rate limits + channel-normalized conversation│
  │ policy router + deterministic action state machine          │
  └─────────┬───────────────────┬───────────────────┬──────────┘
            │                   │                   │
            ▼                   ▼                   ▼
      Approved RAG         AI/SIB gateway      CRM handoff queue
      (citations)       (read-only response)  (agent + SLA + summary)
            │                   │                   │
            └───────────┬───────┘                   │
                        ▼                           ▼
          Customer-care tool facade            CRM operator UI
          (identity, confirmation,              existing conversation,
          idempotency, audit, domain APIs)     tasks and activity)
                        │
                        ▼
       Appointments · labs · pharmacy · memberships · benefits
```

The LLM interprets a request and may propose a permitted operation. It never receives direct database credentials, never calls a business service directly, and never turns an unconfirmed natural-language request into a state-changing action.

## Customer-care policy

### Supported in pilot

1. Approved FAQs: operating hours, service availability, process guidance, policy explanations and document requirements.
2. Authenticated, read-only status: appointment, lab order/report availability, pharmacy order, membership and support-ticket status.
3. Appointment discovery: verified doctors, prices, locations and available slots returned only from authoritative APIs.
4. Human escalation: requests outside confidence/policy, complaint handling, payment/claims disputes, clinical content, abuse, vulnerable users and urgent-symptom signals.

### Explicitly prohibited in pilot

- diagnosis, differential diagnosis, medication changes or clinical treatment advice;
- free-form health-record retrieval or clinical-document summarization to unauthenticated/support users;
- creating, cancelling or rescheduling an appointment without identity verification and explicit confirmation;
- claim approval/denial, refunds, wallet changes, payments or insurance eligibility decisions;
- generating facts not returned by an approved source/tool; and
- silent cross-tenant lookup, cross-channel identity linkage or automated sharing of patient information with employers/family members.

## Core data model

Create a focused migration, prefixed consistently with the existing migration convention. Every customer-care row must include `tenant_id`, timestamps and actor/audit fields.

| Table | Purpose | Key fields |
|---|---|---|
| `cc_knowledge_documents` | Approved FAQ/process corpus | `tenant_id nullable`, `scope`, `title`, `source_uri`, `owner_user_id`, `version`, `status`, `review_due_at`, `published_at`, `revoked_at`, `content_hash` |
| `cc_knowledge_chunks` | Retrieval units | `document_id`, `chunk_index`, `content`, `embedding`, `metadata`, `citation_label` |
| `cc_conversations` | Channel-neutral customer-care state | `tenant_id`, `crm_conversation_id`, `subject_type`, `subject_id`, `channel`, `status`, `purpose`, `consent_snapshot`, `risk_level`, `last_message_at` |
| `cc_handoffs` | CRM operator transfer | `conversation_id`, `reason_code`, `summary`, `priority`, `queue_id`, `assigned_to`, `sla_due_at`, `status`, `created_by` |
| `cc_action_proposals` | Proposed and confirmed writes | `conversation_id`, `tool_name`, `request_hash`, `payload`, `status`, `confirmation_token_hash`, `expires_at`, `idempotency_key`, `result_ref`, `approved_by` |
| `cc_events` | Immutable operational/audit event stream | `tenant_id`, `conversation_id`, `event_type`, `actor_type`, `actor_id`, `data`, `created_at` |
| `cc_evaluations` | Offline/online quality evidence | `release_id`, `scenario_id`, `category`, `expected_outcome`, `actual_outcome`, `pass`, `reviewer_id` |

### Isolation rules

- Resolve tenant and principal only from authenticated server-side claims; never trust request tenant IDs, tool arguments or model output.
- A global support document is readable only when it is published and within review date. Tenant content is filterable only to its owning tenant.
- Never embed raw clinical records into the support corpus. Patient-specific information is obtained only through a narrow, authenticated tool at request time.
- Store minimal transcripts. Apply approved retention schedules, legal hold behavior and user-access/export/deletion handling before pilot launch.

## API contract

All routes are mounted under `/api/customer-care`. They use current Mediqzy authentication/middleware and return a stable envelope: `{ success, data, error?, requestId }`.

### Channel and customer endpoints

| Route | Method | Auth | Behaviour |
|---|---|---|---|
| `/conversations` | `POST` | current channel/user auth | Create/find a self-owned conversation. Channel metadata is normalized server-side. |
| `/conversations/:id/messages` | `POST` | conversation subject only | Validate input, apply policy, retrieve approved knowledge, create response/event or handoff. |
| `/conversations/:id` | `GET` | subject or authorised CRM agent | Return redacted conversation state, citations and permitted message history. |
| `/conversations/:id/handoff` | `POST` | policy service/authorised actor | Create idempotent handoff with reason and safe summary. |
| `/actions/:proposalId/confirm` | `POST` | verified subject | Consume one-time confirmation after re-authentication where required. |

### CRM endpoints

| Route | Method | Capability | Behaviour |
|---|---|---|---|
| `/crm/queues` | `GET` | `communication:read` | List tenant-scoped AI/human handoff queues and SLA state. |
| `/crm/handoffs/:id/assign` | `POST` | `communication:write` | Assign to an eligible CRM operator; write audit event. |
| `/crm/handoffs/:id/resolve` | `POST` | `communication:write` | Resolve with disposition and operator note. |
| `/crm/conversations/:id/ai-summary` | `GET` | `communication:read` | Return server-generated, redacted summary and citations. |
| `/crm/knowledge/*` | CRUD | `communication:configure` | Draft/review/publish/revoke support knowledge with versioning. |

### Transaction facade

The only model-visible actions in pilot are:

```text
search_service_knowledge
get_available_slots
get_self_appointment_status
get_self_lab_order_status
get_self_pharmacy_order_status
get_self_membership_status
create_appointment_proposal
create_reschedule_proposal
create_cancellation_proposal
create_handoff
```

Write-like methods create a proposal only. The domain operation executes only after all of the following are true:

1. authenticated subject matches the service record;
2. the request has a valid purpose/consent and is in the permitted tenant;
3. the server has re-read current authoritative availability/state;
4. the user confirms a clearly rendered action summary; and
5. a server-generated idempotency key has not been consumed.

The facade must return deterministic domain errors such as `IDENTITY_VERIFICATION_REQUIRED`, `ACTION_CONFIRMATION_REQUIRED`, `SLOT_NO_LONGER_AVAILABLE`, `CONSENT_REQUIRED`, and `ESCALATION_REQUIRED`; do not turn exceptions into model prose.

## AI and retrieval design

### Agent identity

Add a dedicated `customer_care` agent to the existing registry. It has no patient clinical tools, no system tools, no direct finance/claim tools and no broad read scope. Its output modes are restricted to:

- `answer_with_citations`;
- `ask_clarifying_question`;
- `present_verified_options`;
- `create_action_proposal`; or
- `escalate_to_human`.

Every response includes machine-readable metadata: `mode`, `policyVersion`, `knowledgeDocumentIds`, `citationIds`, `confidenceBand`, `handoffRequired`, `toolCalls`, and `modelRoute`.

### Retrieval controls

1. Retrieve only published, non-expired documents matching tenant, purpose, audience, language and product/service tags.
2. Rerank and enforce a minimum evidence threshold; no qualifying source means a safe response or handoff.
3. Preserve title, document version, chunk ID and exact supporting span. The user-facing answer renders concise citations.
4. Treat retrieved documents, customer messages and tool results as untrusted data. They cannot change system instructions, authorization or tool selection.
5. Review global/tenant support content on a defined cadence. Revoke content immediately when policy/pricing/availability changes.

### Model-routing plan

Keep the current SIB gateway as the single model boundary. The customer-care service calls SIB with a restricted request schema; it does not connect directly to third-party model APIs or a future GPU server.

Evaluate vLLM only behind a private network endpoint and an authenticated Mediqzy gateway. vLLM is OpenAI-compatible, but its own documentation warns that API-key protection does not secure all server endpoints; network isolation and reverse-proxy/service authorization are mandatory. [vLLM OpenAI-compatible server](https://github.com/vllm-project/vllm/blob/main/docs/serving/online_serving/openai_compatible_server.md)

Benchmark candidate models in English, Hindi and selected supported Indian languages for:

- policy adherence and safe refusal;
- factual support/citation precision;
- tool-selection accuracy;
- prompt-injection resistance;
- latency, concurrency, GPU cost and failure recovery; and
- handoff/escalation recall.

Do not select a model based only on general benchmarks or licence statements.

## CRM-native handoff design

Handoff is a first-class state transition, not a sentence asking the user to contact support.

| Trigger | Result |
|---|---|
| Low retrieval confidence, contradictory source, expired source | `knowledge_uncertain` handoff |
| Clinical, emergency, self-harm, abuse or safeguarding signal | immediate high-priority safety route with approved guidance |
| Identity/access/consent failure | `verification_required` handoff or self-service recovery flow |
| Payment, claim, refund, insurance dispute or complaint | specialist queue handoff |
| User requests human support | customer choice is respected immediately |
| Transaction fails/ambiguous completion | `action_reconciliation_required` handoff; never repeat a potentially completed action |

The CRM panel shows: customer/channel, verified identity state, intent, safe summary, citations used, requested operation, completed tool results, handoff reason, SLA, assignment and full audit history. It must not reveal model system prompts, secrets or data outside the operator's permitted tenant/role.

## Security, privacy and safety gates

1. Enforce the existing ring-fencing, role/capability and tenant middleware on every route.
2. Use request correlation IDs, structured security logs and immutable customer-care events; redact tokens, credentials and unnecessary PHI.
3. Apply per-principal, per-channel and per-tenant rate limits; cap message length, attachments and tool iterations.
4. Validate every tool argument with server-side schemas. The model cannot select its tenant, user, record identifier or permissions.
5. Do not send regulated data to an unapproved provider. Document the model route and data classification on every conversation/action event.
6. Require explicit confirmation for appointment changes; require the domain service to revalidate availability immediately before commit.
7. Treat all claim/payment/benefit outcomes as human-controlled in the pilot.
8. Give urgent-symptom flows approved emergency-care direction and immediate escalation. Do not rely on delayed email/SMS alone.
9. Apply threat modelling for prompt injection, tool abuse, cross-tenant leakage, account takeover, replay, duplicate delivery and malicious knowledge uploads.
10. Complete applicable privacy, clinical governance, retention and Indian regulatory review before using live patient data.

## Quality gates and test plan

### Automated tests

- unauthenticated, wrong-role and cross-tenant request rejection;
- customer cannot read another person's conversation, order, appointment or handoff;
- model-provided tenant/user/record IDs are ignored or rejected;
- unpublished, expired, revoked and wrong-tenant knowledge never retrieves;
- every answer that makes a factual service claim includes valid evidence, otherwise escalates;
- prompt injection in customer text and retrieved documents cannot invoke prohibited tools;
- every write requires confirmation and has stable idempotency under timeout/retry;
- booking/cancellation/reschedule revalidates current domain state;
- handoff de-duplicates, preserves ordering and meets queue/SLA rules;
- model, embedding, retrieval and notification outages degrade to safe handoff without data loss; and
- transcript/audit retention and export/deletion behavior follows approved policy.

### Pilot scorecard

Set numerical thresholds before pilot. At minimum measure:

| Metric | Required pilot measurement |
|---|---|
| Citation support rate | Percent of factual replies with valid source spans |
| Unsupported-claim rate | Human-reviewed hallucination/policy breach rate |
| Escalation precision/recall | Correct transfer of high-risk, uncertain and requested-human cases |
| Action success/duplicate rate | Confirmed domain completion and zero unintended duplicate writes |
| Latency | P50/P95 first-response and full-response time by channel/language |
| Safety blocks | Injection, cross-tenant, consent and risky-action blocks |
| Operator experience | Queue acceptance, summary usefulness, time-to-resolution and reopen rate |
| Availability | Retrieval/model/tool/handoff dependency failures and safe fallback rate |

## Deployment and rollback

1. Deliver as additive migrations and route families. Do not change existing CRM or patient chat contracts in place.
2. Feature-flag by tenant and channel. Default off until a tenant has approved support content, trained agents and monitoring.
3. Start internal-only, then one low-risk tenant/cohort; enable authenticated read-only support before transactional actions.
4. Maintain a kill switch that disables AI responses and sends new conversations to the CRM queue without deleting transcripts, proposals or audit events.
5. Roll back by disabling the tenant/channel flag, retaining the last known-good knowledge corpus and routing model/tool failures to human support.
6. Do not replay uncertain transactional actions. Reconcile them against the authoritative domain service first.

## Explicit future decisions

- **Chatwoot:** deferred; reassess only if the CRM-native queue cannot meet agent-workspace requirements.
- **LangGraph:** evaluate only when durable external workflow state/checkpointing is required beyond the current Node orchestration. It must sit behind the same customer-care API and authorization contract.
- **Medplum:** consider only for a future FHIR interoperability programme; it is not required for customer-care implementation.
- **Agent Chat UI:** do not deploy as a production CRM surface. Its upstream documentation requires custom production authentication; it is a prototype/reference, not an authenticated Mediqzy embed. [Agent Chat UI production guidance](https://github.com/langchain-ai/agent-chat-ui)
- **Voice:** defer until text-channel quality, escalation and consent controls have passed pilot acceptance.
